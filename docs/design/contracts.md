# Metis contract design

This document describes the on-chain contracts in the new design of bridge.md: what each one does, who calls it and when, and how proofs are verified.

There are three business contracts. Proof verification is always routed through the Gateway to a specific verifier:

| Contract | Chain | Responsibility |
| --- | --- | --- |
| `MetisRollup` | L1 | Receives the sequencer's data submissions (commit), verifies proofs and performs finalization (finalize) |
| `MetisL1Bridge` | L1 | Escrows deposits and maintains the deposit tree; releases withdrawals against finalized withdrawal roots |
| `MetisL2Bridge` | L2 | Receives the synced deposit roots so that users can claim deposits; records withdrawals |
| `ZKMVerifierGateway` | L1 | Routes a proof to the matching verifier by the first 4 bytes of the proof |
| Groth16 / Plonk / shrink verifier | L1 | Verifies proofs of the corresponding format |

## 1. Two user paths

**Deposit (L1 to L2)**

1. The user calls `MetisL1Bridge.deposit`.
2. The L2 consensus layer calls `MetisL2Bridge.syncDepositRoot`, which syncs the L1 deposit root to L2.
3. The user, or a relayer paying on the user's behalf, calls `MetisL2Bridge.claim` and claims with a Merkle path. The funds go to the L2 address named in the deposit.

After the claim the funds are usable on L2, but they count as finalized only after a later finalize has checked the synced root.

**Withdrawal (L2 to L1)**

1. The user calls `MetisL2Bridge.withdraw`.
2. The sequencer calls `MetisRollup.commitBatches`, which commits the L2 data containing this withdrawal to L1.
3. The proposer calls `MetisRollup.finalize` and submits a proof that covers this data.
4. The user calls `MetisL1Bridge.relay` and claims on L1 with a Merkle path.

## 2. Why the OP Stack contracts are not reused

op-succinct replaces only the OP Stack output oracle. Deposits, withdrawals and message passing still use OP's original contracts such as `OptimismPortal2`. Metis cannot copy this approach, because OP's L1 contracts and its L2 are designed as a set:

| What OP's L1 contracts require of L2 | Metis today |
| --- | --- |
| A withdrawal predeploy at a fixed address, whose storage is the evidence for withdrawals | A predeploy with the same name exists, but it is the OVM-era version: its storage layout differs, and L1 verifies against the SCC state root, not an output root |
| A dedicated deposit transaction type, generated by the derivation layer from L1 receipts | No dedicated type. Deposits enter a queue on L1, and the sequencer packs them into transactions marked "from the L1 queue" |
| A system transaction at the start of every block that writes L1 information | None |
| An OP-format output root | There is no output root on L1. The SCC stores the Merkle roots of state root batches |

Metis's L2 execution layer was forked from an early OP version and has evolved independently since. Filling the gaps in the table above amounts to a full Bedrock migration, which is far more work than implementing three new contracts.

So bridge.md chooses to design a minimal set of contracts that fits the existing L2: deposits use the L1 deposit tree plus the root that L2 syncs, withdrawals use the L2 withdrawal tree, and committed data is committed to by a chained batch hash.

- Deposits: the L1 deposit tree plus the root that L2 syncs

    - The L1 deposit tree. When a user deposits on L1, MetisL1Bridge locks the funds, appends the deposit as a leaf to a Merkle tree, and stores the root after every append (depositRootAt).

    - The root that L2 syncs. L2 needs to know which deposits exist on L1, but it does not carry them over one by one; only the root is synced. The root is written into MetisL2Bridge by the L2 consensus layer.

    - Claiming. Anyone holding the deposit contents and a Merkle path can prove on L2, against a synced root, that "this deposit is in the tree"; the L2 bridge marks it claimed and mints.

    - Who guarantees that the synced root is real. The L2 bridge links the synced roots into a chained hash, which goes into the output root. At finalize, `MetisRollup` reads depositRootAt from `MetisL1Bridge` and recomputes this chain; if they do not match, it rejects. A sequencer cannot sync a false root and pass finalize.

- Withdrawals: the L2 withdrawal tree

    - The direction is reversed and the structure is the same. The user calls withdraw on L2, and MetisL2Bridge appends the withdrawal to a Merkle tree on L2.

    - The root of this tree is a component of the output root. At finalize it enters the L1 contract with the proof and is stored there.

    - The user then calls relay on L1 and claims against this root with a Merkle path.

    - Withdrawals do not need a "sync" step, because the finalize proof already guarantees that the root is correct.

- Batch hash: a chained hash

  The blobs the sequencer submits do not use a tree but a hash chain: each blob's hash is appended in turn to the previous value.

## 3. `MetisRollup`

| Function | Caller | When called |
| --- | --- | --- |
| `commitBatches` | sequencer | Whenever a group of blobs has accumulated. Under bridge.md's assumption of 40 batches per day, about once every 36 minutes when carrying 1 blob and about once every 3.6 hours when carrying 6 |
| `finalize` | Anyone, usually the proposer | After the aggregation proof is complete |
| `revertCommits` | owner, which should be the governance timelock | When the sequencer has committed wrong data that is not yet finalized |
| `addConfig`, `removeConfig`, `setSequencer` | owner | At deployment, when upgrading the proof program, and when replacing the sequencer |

**Committing data: `commitBatches`**

The sequencer calls it with one transaction that carries 1 to 6 blobs. Each blob is one batch. The contract does three things:

1. Checks that the previous hash declared by the caller equals the latest commit record in the contract, which guarantees that commits link up in order.
2. Reads the hash of every blob in this transaction and appends each in turn to a hash chain. The result must equal the value declared by the caller; a wrong blob order fails outright.
3. Reads the hash of the previous L1 block as the anchor, hashes it together with the chain value, and stores the result.

In step 2 the contract reads the hashes of the blobs carried by the current transaction through the BLOBHASH opcode that the EVM provides. Being able to read this hash shows that the corresponding blob was published to Ethereum with this transaction.

The anchor in step 3 lets the proof program authenticate the L1 blocks that L2 blocks reference; see l1-anchor.md.

**Finalization: `finalize`**

Anyone can call it. The caller supplies the target position, the three components of the end state (block hash, state root, withdrawal root), the list of deposit counts that L2 synced, and the proof. The contract:

1. Checks that the target is a commit boundary that has been committed and not yet finalized.
2. Reads the record of the last finalize from storage as the starting point. The caller cannot choose the starting point.
3. Following the list of counts, takes the corresponding deposit roots from the history in `MetisL1Bridge` and rebuilds the deposit-sync chain. Every count must exist on L1.
4. Computes the new output root from the three components and the rebuilt chain value.
5. Assembles the starting point, the end point and the configuration into the public values and hands them to the Gateway to verify the proof.
6. Stores the new record after verification succeeds.

There is no proposer whitelist, no optimistic mode, and no automatic release after a timeout. The passage of time never finalizes a batch; only a valid proof can.

**Reverts and governance**

- `revertCommits` can revert only commits that are not yet finalized. Finalized ones can never be reverted.
- The contract can register several configurations at the same time. Each contains an approved proof program and a rollup configuration. To upgrade, add the new configuration first, then remove the old one after the proposer has switched; finalize is not interrupted.
- Governance roles should be placed behind a timelock.

## 4. `MetisL1Bridge`

| Function | Caller | When called |
| --- | --- | --- |
| `deposit` | User | When they want to move METIS to L2 |
| `relay` | User or a relayer paying on the user's behalf | After the data containing the withdrawal is finalized |

- **`deposit`** escrows the user's METIS, appends the deposit as a leaf to an append-only Merkle tree, and records the root at that point.
- **`relay`** takes the withdrawal contents and a Merkle path. The contract reads the withdrawal root stored by some finalize from `MetisRollup`, verifies the path, checks that this withdrawal has not been claimed, and then releases the funds.

The withdrawal tree only grows, so any finalized withdrawal root that is not earlier than the withdrawal can be used to claim it; the user does not have to wait for one particular finalize.

## 5. `MetisL2Bridge`

| Function | Caller | When called |
| --- | --- | --- |
| `syncDepositRoot` | System address of the L2 consensus layer | After observing a change in the L1 deposit root, at the agreed frequency |
| `claim` | User or a relayer paying on the user's behalf | After a root that includes their deposit has been synced to L2 |
| `withdraw` | User | When they want to move METIS back to L1 |

- **`syncDepositRoot`** writes an L1 deposit root and the corresponding deposit count, and accumulates it into the deposit-sync chain. Counts must increase.
- **`claim`** verifies that the deposit leaf is under some synced root, checks that it has not been claimed, and then mints the same amount of METIS to the L2 address named in the deposit.
- **`withdraw`** burns the user's METIS, appends the withdrawal as a leaf to the withdrawal tree, and updates the withdrawal root.

`syncDepositRoot` does not verify whether the root is genuine; that verification happens in finalize on L1. If L2 syncs a root that does not exist on L1, the rebuilt chain value will not match, and this data cannot be finalized. Therefore **METIS on L2 does not count as finalized before finalize**.

## 6. How proofs are verified

**Public values.** The proof binds seven values. The `MetisRollup` contract assembles all of them itself. The caller can influence only the three state components, and these are constrained by the proof. The public values do not name the submitter, so the same proof can be submitted from any address:

| Value | Source |
| --- | --- |
| L2 chain ID, rollup config hash, range program vk commitment | Configuration registered in the contract |
| Start batch hash, start output root | The last finalize record stored by the contract |
| End batch hash | The commit record stored by the contract |
| End output root | Computed by the contract from the three components given by the caller and the deposit-sync chain it rebuilds itself |

The `MetisRollup` contract does not compare these values one by one. It encodes them and hands them to the verifier, and the public values committed in the proof must be exactly the same. So if the proof starts from a different starting point or executes different data, or if the caller misreports the withdrawal root, verification fails.

**output root.** The commitment to the end state. It is the hash of five values: the version number, the state root, the withdrawal root, the deposit-sync chain and the block hash.
It has the same structure as the OP Stack output root, with the deposit-sync chain added.

**Proof formats.** The aggregation proof can be Groth16, Plonk or shrink. The three formats use the same envelope: the first 4 bytes are a prefix of the hash of the corresponding verification circuit's vk, followed by the proof contents. The `ZKMVerifierGateway` contract reads these 4 bytes and routes the proof to the registered verifier, and the verifier checks them once more itself. Which formats are accepted is decided by governance, which registers or freezes routes on the `ZKMVerifierGateway` contract.

## 7. Gas budget

The baseline is the prototype measurements in bridge.md. Re-measure after implementation:

| Call | Budget |
| --- | --- |
| `commitBatches`, 1 blob | about 55k |
| `commitBatches`, 6 blobs | about 66k |
| `finalize`, excluding proof verification | 75k to 120k, plus about 2.1k per deposit count |
| Proof verification, shrink | about 13.7M |
| Proof verification, Groth16 | about 230k |
| `deposit` | 105k to 155k |
| `relay` | about 96k |
| `syncDepositRoot` | about 89k |
| `claim` | 81k to 99k |
| `withdraw` | about 122k |

The cost of `finalize` grows with the number of times L2 synced a deposit root within the range. When syncs are too frequent and the interval between finalizes is long, it can approach the per-transaction gas limit. There are two mitigations: the L2 consensus layer limits the sync frequency; the proposer uses segmented finalization by sync count, see proposer.md.
